# ADR-0001：开发环境与基础端口选择

- 状态：已接受
- 日期：2026-08-06
- 决策人：InsightForge 项目

## 背景

InsightForge 处于阶段 0（工程基座）。本机已有的 Miniconda base 环境为 Python 3.13，并存在 `ai_backend`、`langgraph` 等无关环境。后端技术栈为 FastAPI，未来本地与容器化两种运行形态并存，因此需要先确定语言运行时、依赖管理与端口分配。

## 决策

1. **采用 Python 3.12**，不使用 base 环境的 3.13。
   - 3.12 为 LangGraph、向量检索等生态在当前阶段的稳定目标版本，兼容风险低于 base 的 3.13。
   - 不与 base 及现有无关环境混用依赖，避免污染。
2. **Conda 只管理解释器与环境隔离**；项目依赖全部由 `backend/pyproject.toml` 管理。
   - 依赖清单进仓库、可复现、随代码演进；Conda 环境可随时按 `environment.yml` 重建。
   - 不引入 Poetry、uv 或 pipenv。
3. **本地 FastAPI 使用 8001**，不使用 8000。
   - 本机 8000 已被 Windows http.sys 内核驱动注册（`HTTP://LOCALHOST:8000/`），绑定会失败；8001 已确认空闲。
4. **未来 Docker 内使用 8000，宿主机映射 8001:8000**。
   - 容器内部统一 8000（标准服务端口），对外通过 8001 暴露，与本机本地运行端口一致，切换无感知。

## 后果

- 本地开发始终用 8001 访问 API；容器部署时由 Compose 负责映射，应用本身可保持不变。
- 若 8000 端口后续可释放，或 3.12 兼容性出现实际问题，本决定允许基于真实兼容性与部署环境调整。
